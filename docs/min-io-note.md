# MinIO 与对象存储核心笔记

## 1. 基础概念

### S3 (Simple Storage Service)

- 亚马逊 AWS 推出的对象存储服务协议，现已成为整个对象存储领域的**行业接口标准**。所有主流对象存储服务（阿里云 OSS、腾讯云 COS、MinIO 等）都兼容 S3
  API。

### MinIO

- 基于 Go 语言开发，主打高性能（极其夸张的读写吞吐量）。
- 完美兼容 S3 API。
- 可以把它总体理解为一个专门用来存取未结构化数据（图片、视频、日志、发票等）的强大“文件数据库”。

## 2. 核心概念：Bucket（存储桶）

### 2.1 Bucket 与传统文件夹的本质区别

在原生 JavaScript (如 Node.js `fs` 模块) 或操作系统的文件系统中，并不存在 Bucket 的概念。

- **硬盘文件夹（多层级）**：真正的树状结构，必须要先有 `uploads/` 文件夹，才能往里面存 `1.jpg`。
- **MinIO Bucket（扁平化）**：对象存储**没有真实的文件夹结构**。当你上传路径为 `uploads/blog/1.jpg`
  的文件时，底层并没有层层新建文件夹，而是直接提取这整整一长串字符串，作为了这个文件**唯一的 ID（Object
  Key）**。
- **身份定位**：Bucket 是一个隔离的顶级命名空间，你可以把它看作是被系统直接分配给你的一块“外置硬盘分区组合”。

### 2.2 Bucket 高级配置选项

Bucket 可以绑定各种全局“特权”和高级规则，这是普通本地文件夹远远做不到的：

1. **Versioning（版本控制）**：
   - 开启：同名文件覆盖时，会隐式保存所有历史版本记录，随时可以一键回滚。
   - 关闭：新文件直接无情覆盖旧文件。
2. **Object Lock（防篡改锁定）**：
   - 关闭：对象可以随意删除修改。
   - 开启：配合保留模式，使对象在一定时间内绝对无法被删除（WORM：Write Once Read Many 设计原则）。
   - 保留模式（Mode）：
     - **Compliance（合规模式）**：最严苛模式。任何人都无法提前修改或删除该文件，包括系统最高管理员和 Root 账户，一直要等到设定的保护期结束为止。
     - **Governance（治理模式）**：普通用户无法修改，但拥有特殊权限（如特定 IAM 策略）的管理员可以“破例”解禁并删除。

## 3. 项目架构与实战经验

### 3.1 为什么项目要接入 AWS S3 SDK？

本项目**没有**使用官方原生的 `minio` NPM 包，而是接入了 **AWS S3 官方 SDK (`@aws-sdk/client-s3`)**。

- **原因**：因为所有相关库最终都遵循并且底层实现 S3 标准。在前端 Node 生态中，使用最正统、最久经考验的 AWS
  SDK 属于绝对的业界最佳实践。未来如果要从本地 MinIO 无缝迁移到其他云厂商（阿里云 OSS、腾讯云）的云端，代码的迁改成本几乎为零。

### 3.2 两种 SDK 对 Endpoint（连接地址）的奇葩差异

- **AWS S3 SDK（本项目采用）**：`endpoint` **必须明确带有** `http://` 或 `https://`
  的协议前缀。如果不带协议，SDK 内部可能会默认尝试通过 `https`
  连接远程 AWS 官方的云端服务器，导致明明是在调本地服务却莫名其妙连接超时失败。
- **MinIO 官方 SDK（如各语言原生官方包）**：`endpoint` **严格禁止**带有 HTTP 协议头。它只接受类似
  `127.0.0.1:9000`
  这样的 IP+端口字符串。至于要到底走 HTTP 还是 HTTPS，全靠另一个单独的布尔值参数（如 `Secure: false`
  或 `useSSL: false`）来唯一控制。

## 4. 业务场景：Bucket 的划分策略

在实际开发中，建立多少个 Bucket 取决于**业务规模**和**数据管控策略需求**。一般有三种主流演进策略：

1. **“单桶”策略（小型 / 展示类项目）**
   - **方案**：全量数据塞进一个唯一的 Bucket，内部纯靠前缀（即假文件夹，如
     `avatars/`、`blog/`）来区分模块。
   - **场景**：如本博客系统，系统产生需要落盘保存的图片几乎全是供外网自由浏览的，权限非常统一（都需要配置为“公开读取”），管理极其简单省事，避免了内部频繁切换配置。
2. **“按权限”双桶隔离策略（中大型安全项目）**
   - **方案**：严格分为类似于 `project-public` 和 `project-private` 两个物理 Bucket。
   - **场景**：有的文件（头像、封面图）需要被公网游客高速访问，而有的文件（私密文档、个人真实身份证件记录）绝对不能通过一根 URL 轻易外泄泄露。在对象存储运维中最忌讳在一个 Bucket 内去为成千上万个图片逐一单独配置 ACL 小权限，而是必须直接通过**“分桶”**这个顶层容器从物理上来一次性加持权限壁垒保障。
3. **“按生命周期”隔离策略（垃圾回收降本增效）**
   - **方案**：按照保存的时间周期长短分为临时桶与长效桶。
   - **场景**：临时存放各类未最终敲定正式发布的文章配图（甚至只是一些日志、冗余分析报表），给这个特定的 Bucket 简单配置一下策略：“所有文件自产生开始 30 天效期满后，服务底层脚本发力自动抹除清洗”，这就避免了自己额外写定时器和垃圾检测逻辑去维护清理磁盘。

## 5. 核心代码设计模式：如何吃透 S3 权限逻辑

### 5.1 自动初始化 Bucket（容错探测设计）

在后端应用启动或首次需要上传落盘尝试建立连接时，通常需要这么进行一段初始化逻辑，以实现你的微服务的**免人工辅助的”零配置冷启动“**：

```typescript
// 1. 发送 HTTP HEAD 请求“叩门敲板”，它非常轻量，仅仅探测 Bucket 是否存在响应，绝不拉取多余内容数据
try {
  await s3Client.send(new HeadBucketCommand({ Bucket: bucketName }));
} catch {
  // 2. 如果不存在（未命中自然抛错，抛出类似于 404 报错硬切入到了 catch 中），让代码逻辑在兜底机制下自动替你“无感”创建出它来
  await s3Client.send(new CreateBucketCommand({ Bucket: bucketName }));
}
// 3. 不管你是旧瓶还是新酒，出库后我都强制为你全覆盖上最新版的业务必需读写权限配置...
```

> 因为受阻于架构理念，S3 SDK 乃至底层根本没有提供类似于 `isBucketExist`
> 这种顺手返出布尔值的便捷方法，所以这段充满 `try...catch` 然后配合极其轻量的 `Head`
> 请求的探测组合拳，就是各大平台封装底层库时被公认的、最高效的标准解法。

### 5.2 揭秘 Bucket 权限配置（IAM Policy）

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": "*",
      "Action": ["s3:GetObject"],
      "Resource": ["arn:aws:s3:::esti-blog/*"]
    }
  ]
}
```

这段代码是一份纯粹、标准的 **AWS
IAM(身份与访问管理) 权限 JSON 模板**。不管你后面转去了什么生态系统，涉及它的底层都将以此类模版格式为基座运作：

- `Version`：无法人为篡改定义的固定魔法字符串（`2012-10-17` 代表 AWS 第五代语法设计迭代稳定版）。
- `Effect`：`Allow`（代表着它是一条白名单放行规则） 或 `Deny`（代表黑名单拦截）。
  - **核心铁律**：在它的鉴权体系判定下，`Deny`
    享有着绝对的**一票否决权**！当用户发起请求时，它只要触碰哪怕唯一一条 `Deny`
    规则的边界，那么不管其自身之上叠加着多少道 `Allow`
    的放行绿灯护身符，最终结果都将被宣判绝对拦截禁止访问！
- `Principal`：描述这份权力的覆盖受益面积（`*`
  就代表将大范围涵盖着毫无校验防线的、在互联网上畅走的任何一名匿名过客游客）。
- `Action`：界定真正开放允许被执行的神技操作界限名称边界（`s3:GetObject`
  就代表我只开放文件对象对外的抓取 / 读取 / 下载大门，休想动 `Put` 新增和 `Delete`
  删除破坏的心思）。
- `Resource`：圈出的资源版图边界。注意它的特殊格式组合 —— `arn:aws:s3:::esti-blog/*`
  。它最最末尾的小小 `/*`
  极其关键，没有这一笔画龙点睛，这个规则就悲剧地被直接锁在了桶外壳上，完全渗透不进里面的千千万万张存下来的图片，外部自然还是看不到抓不了的。
